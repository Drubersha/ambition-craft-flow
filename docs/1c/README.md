# Обмен данными 1С → LeasePlease: формат файла и ответы на вопросы

**Версия формата:** 1.0 · **Дата:** 15.10.2026 · **Принимающая система:** LeasePlease (учёт аренды ПБ «Хлебозаводская»), https://leaseplease.ru
**Файлы к этому документу:** `1c-export.empty.json` (пустой шаблон), `1c-export.sample.json` (пример с данными), `1c-export.schema.json` (JSON Schema для автоматической проверки на стороне 1С).

---

## 1. Коротко

- 1С раз в сутки, ночью, отправляет один JSON-файл POST-запросом на адрес приёмника. В файле справочники целиком (контрагенты, объекты, договоры, допсоглашения) и документы за последние 6 месяцев (начисления, оплаты, зачёты, сальдо).
- Приёмник проверяет файл по схеме, сопоставляет записи по GUID объектов 1С, создаёт новые, обновляет изменённые, аннулирует исчезнувшие и возвращает отчёт: сколько принято, что изменилось, какие строки отклонены и почему.
- Ничего не удаляется физически и ничего не перезаписывается без следа: каждая загрузка сохраняется как пакет, а прежние значения изменённых записей — в истории. Поэтому правки задним числом в 1С (в пределах полугода) безопасно подхватываются следующим же файлом.

## 2. Транспорт

| Параметр | Значение |
|---|---|
| Адрес | `POST https://leaseplease.ru/api/1c/import` |
| Проверка без записи | тот же адрес с `?dry_run=1` — вернёт отчёт, в базу ничего не попадёт. Для отладки выгрузки |
| Авторизация | заголовок `Authorization: Bearer <токен>`; токен передадим отдельно (не по почте в открытом виде), можно сменить в любой момент |
| Тело | `Content-Type: application/json; charset=utf-8`; допускается `Content-Encoding: gzip` |
| Размер | до 50 МБ. Ожидаемый размер файла по нашей базе (≈50 договоров, ≈600 начислений и ≈600 оплат за полгода) — около 1 МБ |
| Время | ежедневно 01:00–05:00 по Москве. Около 00:00 на сервере идёт ночная пересборка, поэтому не раньше 01:00 |
| Белый список IP | сообщите внешний IP, с которого будет идти запрос, — ограничим приём только им |

**Ответы сервера**

| Код | Что значит | Что делать на стороне 1С |
|---|---|---|
| 200 | файл принят, в теле отчёт (см. ниже) | записать `batch_id` в журнал |
| 400 | файл не прошёл проверку по схеме или ссылки внутри не сходятся; в теле список ошибок с путями (`payments[12].allocations[0].charge_id`) | исправить выгрузку; ничего не записано |
| 401 | неверный токен | проверить токен |
| 413 | файл больше лимита | включить gzip или сузить окно |
| 500 / таймаут | сбой приёмника | повторить через час, до 3 раз; повторная отправка того же файла безопасна |

  "period": { "from": "2026-04-15", "to": "2026-10-15" },
  "counterparties": { "received": 46, "created": 1, "updated": 3, "unchanged": 42 },

## 3. Состав файла и правила

Порядок блоков в файле не важен. Все ссылки (`counterparty_id`, `contract_id`, `property_id`, `charge_id`) должны разрешаться либо внутри файла, либо среди уже загруженных ранее записей.

| Блок | Что передавать | Обязателен |
|---|---|---|
| `source`, `period`, `mode` | откуда файл, окно документов, режим (`window` — обычный ежедневный; `full` — полный снимок по договорённости) | да |
| `counterparties` | **все** контрагенты-арендаторы, включая архивных (`is_active: false`), чтобы ссылки из старых договоров разрешались | да |
| `properties` | **все** объекты аренды, если они ведутся в 1С. Если нет — блок пустой, объекты сопоставляем у себя | нет |
| `contracts` | **все** договоры аренды (действующие, завершённые, расторгнутые) | да |
| `amendments` | **все** допсоглашения как отдельные записи со ссылкой на договор | нет, но очень желателен |
| `charges` | документы реализации (аренда, коммуналка, прочее) с датой в окне | да |
| `payments` | поступления на р/с, ПКО, зачёты взаимных требований, возвраты, корректировки долга с датой в окне | да |
| `balances` | сальдо по счёту 62 на дату `period.to` по контрагентам (желательно по договорам) — только для автоматической сверки | нет |

**Правила окна (`mode: "window"`)**

- Окно = `[сегодня − 6 месяцев; сегодня]`, границы в `period`.
- Документ с датой в окне, которого нет в файле, считается удалённым в 1С: в приёмнике он **аннулируется** (помечается `voided`, из долгов и отчётов исключается, из истории не пропадает).
- Документы с датой вне окна приёмник не трогает.
- Если документ помечен на удаление или непроведён — передавайте его с `is_cancelled: true`, а не выбрасывайте из файла: так разница между «удалили» и «забыли выгрузить» видна явно.

**Правила сопоставления**

- Ключ каждой записи — `id`: GUID объекта 1С (`Ссылка.УникальныйИдентификатор()`). ИНН ключом **не** является (см. 6.3).
- Запись с известным `id`: поля сравниваются; при отличиях запись обновляется, прежние значения уходят в историю с номером пакета. `updated_at` из 1С желателен — он попадает в историю как «когда изменили в источнике».
- Запись с новым `id` создаётся. Повторная отправка того же файла ничего не меняет (идемпотентность).

## 4. Типы и форматы значений

| Тип | Формат | Пример |
|---|---|---|
| Дата | `ГГГГ-ММ-ДД`, без времени и часового пояса | `"2026-10-15"` |
| Дата-время | ISO 8601 с часовым поясом | `"2026-10-15T03:00:00+03:00"` |
| Деньги | число JSON, точка — разделитель, до 2 знаков, без пробелов и символа валюты; отрицательные допустимы только в `adjustment` и `return` | `42750.0`, `-1500.5` |
| Площадь, количество | число, до 2 знаков | `45.0`, `283.5`, `2` |
| Ставка | число, до 4 знаков | `950.0`, `279.58` |
| Проценты | число (не доля): НДС 20 → `20`, пени 0,1 %/день → `0.1` | `20`, `0.1` |
| GUID | 36 символов, через дефисы, регистр любой | `"6f1c2a3e-8b4d-4c1e-9a2f-0b7d5e6c1a01"` |
| Строка | UTF-8, без ограничения длины; кавычки-«ёлочки» и ё допустимы | `"ООО «Вектор-Трейд»"` |
| Логическое | `true` / `false` | `true` |
| Нет значения | `null`, **не** пустая строка, не `"нет"`, не прочерк | `"kpp": null` |
| Перечисления | латиницей в нижнем регистре из списка (ниже) | `"bank_in"` |
| Валюта | ISO 4217 | `"RUB"` |
| Телефон, e-mail | как есть, строкой | `"+7 917 000-00-01"` |

**Перечисления**

| Поле | Значения |
|---|---|
| `counterparties[].kind` | `company` — юрлицо РФ; `entrepreneur` — ИП; `person` — физлицо; `foreign` — иностранное лицо (без ИНН) |
| `properties[].type` | `office`, `warehouse`, `retail`, `production`, `coworking`, `land`, `parking`, `other` |
| `unit` (объект и договор) | `sqm` — квадратные метры; `space` — машиноместа; `lot` — лоты |
| `contracts[].kind` | `rent` — аренда; `own_use` — собственные нужды (АХЧ), без начислений |
| `contracts[].status` | `draft`, `active`, `finished`, `terminated` |
| `contracts[].rate_period` | `monthly`, `quarterly`, `yearly`, `one_time` — за какой период указана ставка |
| `contracts[].payment_timing` | `advance` — до N числа предыдущего месяца; `current` — до N числа расчётного; `arrears` — до N числа следующего |
| `contracts[].deposit.status` | `none`, `paid`, `offset` (зачтён), `returned` |
| `charges[].doc_type` | `realization` — реализация (акт/накладная); `act`; `invoice`; `adjustment` — корректировка реализации |
| `charges[].kind` | `rent`, `utilities`, `other` |
| `payments[].doc_type` | `bank_in` — поступление на р/с; `cash_in` — ПКО; `offset` — зачёт взаимных требований; `return` — возврат арендатору; `adjustment` — корректировка долга |

Полное описание с ограничениями — в `1c-export.schema.json`; здесь — смысл полей. «Обяз.» — обязательно ли поле в файле.

### 5.1 `counterparties[]` — арендаторы

| `code` | строка | нет | код справочника |
| `kind` | enum | да | юрлицо / ИП / физлицо / иностранное |
| `name`, `full_name` | строка | `name` — да | краткое и полное наименование |
| `country` | `RU`, `KZ`… | да | ISO 3166-1 alpha-2 |
| `inn`, `kpp`, `ogrn` | строка/null | `inn` — для `company` и `entrepreneur` | для иностранных — `null` |
| `foreign_tax_id` | строка/null | для `foreign` | налоговый или регистрационный номер страны контрагента (BIN, TIN) |
| `legal_address`, `actual_address`, `postal_address` | строка/null | нет | |

### 5.4 `amendments[]` — допсоглашения

Отдельная запись на каждое допсоглашение со ссылкой на договор. В `changes` заполняется только то, что меняется (`rate`, `area`, `end_date`, `payment_day`, `vat_rate`), остальное `null`; изменения, для которых нет поля (реквизиты, объект), — текстом в `changes.other`. Договор в блоке `contracts` при этом должен содержать **действующие** условия (после всех допсоглашений).

| `due_date` | дата/null | нет | срок оплаты; если `null` — приёмник возьмёт из условий договора |
| `amount_without_vat`, `vat_amount`, `amount_total` | деньги | да | три суммы; `amount_total = amount_without_vat + vat_amount` |
| `description` | строка/null | нет | номенклатура или комментарий |

|---|---|---|---|

| `contract_id` | GUID/null | нет | если платёж по одному договору |

Сальдо по счёту 62 на `period.to`: `debit` — долг арендатора, `credit` — аванс. Приёмник сравнивает со своим расчётом и показывает расхождения; на данные не влияет.

## 6. Ответы на вопросы ИТ-директора

### 6.1 Как хранятся данные

- **Где.** Собственный выделенный сервер (VPS, Ubuntu, Docker). База — PostgreSQL 15 (self-hosted Supabase: PostgREST как REST-слой, GoTrue для входа, Storage для файлов). Доступ к базе снаружи закрыт; наружу открыты только HTTPS-порты сайта и API через Caddy с автоматическими сертификатами.
- **Что.** Около 30 таблиц: объекты и папки с планами, арендаторы и их контакты, договоры и допсоглашения, начисления, платежи, счётчики и показания, коммунальные периоды, бюджет, уведомления, журнал действий. Каждая запись несёт `created_at` и `updated_at`; платежи и начисления — отдельные строки-документы, а не агрегаты.
- **Разграничение.** Данные изолированы по владельцу на уровне строк (Row-Level Security): пользователь видит только свои записи, арендатор в своём кабинете — только свои договоры и начисления.
- **Резервные копии.** Три контура: перед каждым обновлением приложения, ежедневно и раз в три дня (хранятся по две копии каждого), плюс именные копии перед ручными изменениями. Копия включает все схемы базы и загруженные файлы; восстановление проверено.
- **Код.** Открытый репозиторий на GitHub, автоматическая сборка и выкладка из ветки `main`.

### 6.2 Как соблюдается историчность

Три уровня.

1. **История условий договора.** Допсоглашения хранятся отдельными записями со ссылкой на договор, своим номером и датой. Договор хранит действующие условия, допсоглашения — что и когда менялось: «ставка 900 → 950 с 01.07.2026». В интерфейсе это видно в карточке договора.
2. **Документы не правятся молча.** Начисления и платежи — самостоятельные документы с датой, периодом и суммой. Если 1С меняет документ задним числом, в следующем файле придёт та же запись (тот же GUID) с новыми значениями: приёмник сохранит прежнюю версию в историю импорта (пакет, дата, поле, было → стало), обновит текущую и отметит в отчёте. Удаление в 1С → у нас аннулирование с датой и причиной, не удаление строки. Так любую цифру в отчёте можно отмотать к конкретному файлу и дате.
3. **Пакеты и журнал.** Каждый принятый файл сохраняется (дата, размер, хэш, отчёт) не меньше 12 месяцев, расхождения между сальдо 1С и нашим расчётом фиксируются по датам. Действия пользователей в интерфейсе пишутся в журнал (кто, когда, что открыл или изменил).

Что уже есть сейчас: уровни 1 и 3 (журнал действий). Хранение версий документов и пакетов импорта (уровень 2) появится вместе с приёмником — это его часть.

### 6.3 Иностранный арендатор без ИНН

- ИНН в нашей системе **не обязателен** и не является ключом. Ключ сопоставления — GUID контрагента из 1С (`id`), поэтому отсутствие ИНН ничего не ломает.
- Для иностранного контрагента передавайте `kind: "foreign"`, `country` по ISO (например `"KZ"`), `inn / kpp / ogrn: null`, а налоговый или регистрационный номер страны — в `foreign_tax_id` (BIN, TIN, номер регистрации). Банк: `bik` — SWIFT, `account` — IBAN. Пример — третий контрагент в `1c-export.sample.json`.
- Начисления и оплаты по нему — в рублях (учётная валюта), как в 1С. Если договор валютный, `currency` договора указывает валюту ставки, а суммы документов остаются рублёвыми по курсу 1С.
- На нашей стороне в карточке арендатора добавятся поля «Страна» и «Налоговый номер (иностр.)»; в реквизитах для актов ИНН/КПП тогда не печатаются.

### 6.4 Взаимозачёт (арендатор оплатил услугой)

Расчёт зачёта остаётся в 1С — там оформляется «Корректировка долга → зачёт взаимных требований» или акт зачёта, и в нём уже определено, какая сумма и какие документы закрыты. Нам нужен результат, а не расчёт. Передаётся он как платёжный документ:

- `doc_type: "offset"`, `amount` — сумма зачёта, `date` — дата акта зачёта.
- `allocations[]` — какие начисления и на сколько закрывает зачёт (как у обычного платежа). Если 1С не хранит разнесение, оставьте массив пустым — закроем старейшие долги по договору.
- `offset` — основание: номер и дата акта зачёта (`basis_doc_*`), встречный документ (`counter_doc_*` — акт выполненных работ, накладная), `description` — чем оплачено («ремонт кровли над офисом 205»), `expense_category` — статья расходов для бюджета («Текущий ремонт»).

Как это считается у нас:

| Показатель | Зачёт учитывается? |
|---|---|
| Долг арендатора, просрочка, собираемость | да — начисление закрыто, как деньгами |
| Поступления деньгами (касса, банк) | нет — зачёт показывается отдельной строкой «зачтено услугами» |
| Расходы в бюджете план/факт | да — сумма зачёта ложится в указанную статью расходов, иначе факт по расходам занижен |
| Сальдо для сверки с 1С | да |

Частичный зачёт (услуга дороже долга или дешевле): в файле — только сумма, на которую зачтено; остаток нашего долга за услугу остаётся в 1С в кредиторке и нас не касается. Если позже зачёт отменят — тот же документ придёт с `is_cancelled: true` или исчезнет из окна, и начисление снова станет неоплаченным.
